### 关于 AGPL 的处理（这条最容易踩）

《总则》举的违规例子正是"把 AGPL 作品装进 MIT 仓库"。
业界做 PDF 文本提取最常用的是 **PyMuPDF（AGPL-3.0）**。

**我的处理是：从一开始就不采用它**，改为自研 `src/pdftext.py`（纯标准库）。
因此本仓库**不含任何 AGPL / GPL / LGPL 代码**，MIT 声明干净成立。
（对照：同挑战的高分方案采用了 PyMuPDF，需要额外写一节来说明这个风险并给替代路径。）

> 原文大意："评审方按 README 与复现脚本无法独立跑通核心结果，且作者不响应 / 不修复。"

| **零第三方依赖** —— 不需要 `pip install`，不需要虚拟环境 | `requirements.txt` 里写明了这一点 |

| **无随机性**：确定性流程，无需固定 seed | — |
| 说明清楚"复现的是什么、不是什么" | `README.md` ｜ `拿来说明.md` §3 |

### 我在复现性上额外做的事

| 加固项 | 说明 |
|---|---|
| **幂等自检** | 术语回正把规则作用到自己的产出上，仍在变化就报错退出 |
| **失败即非零退出码** | 抓取全失败、幂等未通过都会以非零码退出，不把"全败"报成"跑完" |
| **路径与目录名解耦** | 脚本用自身目录定位同级文件，放在任何目录下都能跑 |
| **端到端复跑验证** | 兜底链的"假工程量"就是靠端到端复跑揭穿的（配了却空转） |

### 一处如实说明（不算违规，但必须讲清楚）

**译文本身不会在复现时"重新生成"**。它是 LLM 产出并固化在 `corpus/zh/` 的产物；
商业 LLM 的输出天然不可复现（模型会更新、有随机性）。
因此本项目复现的是**从原文到成品的全部自动化环节**：抽取、切分、校验、回正、建站、报告。

这一点在 `README.md`、`拿来说明.md`、`方案设计.md` 里都写明了，**不含糊其辞**。
如果评审要求"译文本身也必须可复现"，那需要引入离线 MT 引擎（如 Argos Translate）——
但本机装不上（见 `AI日志.md` 决策 1），且离线引擎的通顺度天花板明显更低。
