## 软件团队的代码评审要点

2015 年 2 月 9 日

代码评审是任何协作型软件项目中不可或缺的一环。大型软件系统通常由不止一个人编写，因此一个高效运转的软件团队需要一套稳健的流程，让团队成员和代码库本身都朝着正确的方向前进。

代码评审是一件强有力的工具，它可以：

1. 在系统变化的过程中，帮助团队成员调整自己对该系统的心智模型
1. 确保改动正确地解决了问题
1. 为设计的优点与不足打开讨论空间
1. 在生产环境之前抓住 bug
1. 保持代码风格与组织结构的一致性

把这些好处理解为一份需求层次会很有帮助。

## 让团队成员保持同步

代码评审最关键的作用，是让团队每一位成员都朝正确方向前进。你无法安全地改动一个自己不理解的系统，因此代码评审能让团队在认知上保持一致。当 Bob 为账务子系统提交一个拉取请求时，Amy 在评审 Bob 的代码的过程中，会同步更新自己对那个系统的心智模型。Amy 有机会就自己不理解的部分提问，Bob 也从中受益：他厘清了自己的设计决策，同时把工作讲给了别人听。一个月后当 Amy 需要改动账务子系统时，她对系统的心智模型已经是最新的，可以直接动手。她花更少的时间读代码、在脑子里拼凑系统，花更多时间思考更高层的抽象与设计。每个人都赢了，因为每个人都保持同步。

## 提交一个好的拉取请求

在你写下一行改动系统的代码之前，先问自己下面几个问题：

- *「这是当前最该做的事吗？」* 来自客户、团队内部成员和其他相关方的需求总会相互竞争。在深入动手之前，这能帮你把优先级理清楚。迭代会、冲刺规划会等其他流程也有助于把这件事拉回正轨。
- *「团队是否已经认可这个改动是对的？」* 如果没有，最好先通过邮件或当面发起设计讨论。当大家在改动之前就对设计达成一致时，你的改动更容易被接受。
- *「我怎样才能把这个改动拆成容易评审、容易理解的若干小块？」* 小改动更容易思考和理解。团队能迅速看懂你的改动，好的讨论才会展开。如果你的改动过于庞大，同事会看得两眼发直，你可能只能收获几条风格上的吹毛求疵。
- *「我打算如何测试这个改动，以消灭 bug 并确保正确性？」* 你可能有所在的质量保障部门，但交付能正常工作的优质软件仍然是开发者自己的责任。容易测试的软件通常耦合更低、切分更小、也更容易推理。你必须为所有改动准备好测试方案。

我发现，提前回答这些问题从长远看省去了我很多头疼。你最不愿意看到的就是花几天写好一个改动，最后却因为根本性的设计缺陷或团队分歧被拒。或者你的改动因为没人能验证其正确性而卡住。再说一次，目标是在改动系统的同时，让其他团队成员跟上你的改动。问自己打算如何把工作切成小到一口能吃掉的小块并逐一测试，在很多方面都有好处：

- 它降低了风险
- 它让改动更容易推理
- 它推动你走向更好的设计

你宁愿用手术刀做许多次精准的小切口，也不愿用砍刀来一道巨大的砍痕。在大多数增量式改动中，我更喜欢手术刀式的开发方式，而把砍刀留给删除大段死代码的时候。

## 提交拉取请求

好，现在你已经从团队那里获得了对自己改动的认可，也实现了当初设定的设计。那么，实际提交拉取请求最有效的方式是什么？你为改动付出了很多，希望团队其他成员关注你的拉取请求并快速给出反馈。该怎么做？

还记得我前面说过，代码评审最重要的作用是让团队的集体心智模型保持良好对齐吗？你的其他同事很可能在做与你完全不同的东西，也许在系统的完全另一处。他们的大脑处在完全不同的上下文里，所以你必须弥补这一点，给他们完成评审所需的指引。这意味着你要把改动、改动原因，以及其他无法仅靠读代码获得的相关信息，写成一份条理清晰的说明。不要让同事承担不必要的脑力负担。

我们来看一些拉取请求说明的好例子和坏例子：

坏例子：

```
Title: Fix uninitialized memory bug
Description: 

This is the bug Bob and I talked about earlier. I had
trouble with the compiler but managed to make this work. Let me
know what you guys think.
```

如果你是这条拉取请求的开发者，先停下来，把自己放到代码评审者的位置上体会一下。标题含糊，带来的疑问比答案还多：内存 bug 在哪里？这个改动有多关键？你和 Bob 之前聊的是哪个 bug？编译器上遇到了什么麻烦？这段说明既没有提供关于问题的有用上下文，也没有对改动给出有用的描述。如果这条拉取请求很长，评审者就得先一头扎进代码里，做一番脑力体操来获取上下文，然后才有机会思考这个改动如何融入系统整体一致的设计。

下面是一个改进后的例子，它把改动集说清楚了：

```
Title: Fix process crash on startup from uninitialized memory [#54633]
Description:

This bug was causing process crashes on boot due to a memory
initialization error in our statistics Counter class. I talked this
over with Bob, and we both agree the crashes are a rare edge case
that don't warrant a hot-fix release. Here's a summary of the
changes:

  - Moved the underlying int variable into the class initializer
    to prevent ununitialized memory in the Counter.
  - Reworked the Counter interface to simplify caller conditional
    logic and prevent further off-by-one counting problems.
  - Added a unit test that exposes the crash

Testing: I've verified the test suite still passes, and verified
manually that the crash doesn't happen locally.
```

这份拉取请求说明在几个方面有了改进：标题足够描述性，能给评审者一点简短的上下文，并吸引他点开邮件了解更多。评审者知道这是一次进程崩溃（通常是很糟糕的事），而且还有一个 bug 报告编号，如果他感兴趣，可以读到关于该 bug 报告的更多细节，从而更了解问题。新的说明还指出问题发生的位置，并帮助给出这次修复有多关键的上下文。其中有一份摘要，列出拉取请求在高层结构上的改动，让评审者在看代码之前就在脑中形成改动的图景。代码评审者不应该被自己看到的东西吓一跳。这个例子还说明了做过哪些测试，让评审者相信这些改动经过深思熟虑、充分测试，已经可以合并。让你的评审者更容易成功：把「合并」按钮做得傻瓜都能点。

## 评审者：给出建设性反馈

评审流程中接下来要考虑的环节，是向同事给出建设性反馈。如果目标是清晰与对齐，那么给出高质量的建设性反馈能帮助所有人更好地理解系统，并推动代码变得更好。

避免这样说：

- *「这个设计是坏的。」* 为什么坏？怎么才能改好？这类说法会打击信心，也容易伤人自尊。
- *「我不喜欢这个改动。」* 你为什么不喜欢？你希望改成什么样？不喜欢某样东西没问题，但你应当把想法讲清楚，并给出代码可以如何改进的有用线索。
- *「你能把它改得更清楚一些吗？」* 我现在这样有什么问题？应该怎么重写？哪里不清楚？这类评论本身就不清楚，也没有给出一个简单的改进方向。

而应该这样说：

- *「这段代码如何处理负整数？」* 这条反馈很具体，会促使开发者自己去想清楚各种结果。作为评审者，你可能已经知道这段代码遇到负整数会崩溃，但让开发者自己意识到会更好。这类问题也可能说明测试存在缺口，或者需要进一步明确范围。
- *「这一段我看不明白，我不理解为什么 A 类要和 B 类通信」* 如果开发者没有提供有用的说明，代码结构也不清晰，这类评论有助于推动设计更清晰、代码更干净。
- *「这里看起来你打破了一个接口边界。这会对使用者产生什么影响？」* 你指出了自己发现的问题，同时给了对方善意的假设——他可能是有意为之。这样他就可以思考打破接口边界带来的隐性后果，要么给出这样决定的理由，要么选择修改。

总体而言，把反馈表述成问题，是推动清晰与正确性的好办法，同时也能帮助开发者在未来改进自己的设计。高质量的创意写作小组通常就是这样互相反馈的。在创意写作的场景里，说「我不喜欢这个角色」是有害的；而同一句话可以更清楚地重新表述：「在第一章里你的角色温暖又富有同情心，现在却冷漠又冰冷。他对我来说不像一个真实的人。」这样就有了具体、可以被澄清的反馈，从而把问题找出来。

程序员喜欢解决问题、指出毛病，因此天生就喜欢发现并指出缺陷。把代码评审当成证明自己聪明、从同事代码里挑毛病的机会，这种诱惑很大。不要这么做。代码评审是让更多双眼睛看到改动、找出关键问题的方式，但你的目标应当是以鼓励团队成员在解决问题的同时提升技能的方式去评审。

## 风格问题

大括号位置、变量 / 函数命名、缩进和空格问题应当被处理，但它们并不是好的代码评审的核心目的（注意，我把它们放在了代码评审金字塔的顶端）。如果你发现团队把 90% 的时间都花在挑剔缩进和变量名上，那很可能是在把大家的时间浪费在大部分可以自动化的事情上。写一份风格指南，在提交时强制检查缩进和空格问题，把时间用在价值更高的问题上。我并不想贬低一致风格的重要性。恰恰相反，保持一致的惯用风格是让代码库易于阅读和理解的最简单方法之一。但如果你把所有代码评审都花在这些简单任务上，就该问问自己：是不是在回避更困难、也更重要的那份工作——让团队保持认知对齐，并思考更高层次的设计。
